# 開発者の OCR 利用例外

管理者が `ai_quota.settings.developer_user_id` に Supabase user ID を明示設定すると、その1アカウントの OCR だけが、`unknown_usage_breaker` と個人・全体の日次回数制限の対象外となる。期限や追加回数の上限はなく、無効化まで有効。チャットと CSV 列推定には通常の制限を適用する。

各 OCR 予約時に例外適用の有無を `ai_quota.requests.daily_limit_exempt` に保存する。例外付き要求は日次の個人・全体件数には含めない。設定の無効化や対象変更後も過去の判定は維持し、通常ユーザーの全体枠を消費しない。無効化後の新規要求は通常どおり計上する。既存の履歴は非例外として扱う。

緊急停止、個人・全体の同時実行数、実測月額上限、利用量・履歴の記録は全要求に適用する。利用量を取得できない場合は通常どおり `unknown_usage` となり、通常ユーザーのブレーカー判定にも含まれる。実測できた開発者 OCR の費用も月額集計に含める。

**費用の制約:** 月額上限は取得できた利用量に基づく。`unknown_usage` の費用は不明なため集計できず、期限・回数のない開発者例外では、失敗が続いても実際の請求額に上限を保証できない。管理者は稼働状況と外部の請求情報を監視し、デバッグ終了時に例外を無効化する。

## 権限と管理

認証済みユーザーIDは既存バックエンドが Supabase `auth.get_user` で検証した結果を使用する。`ai_quota_backend` は任意のIDを claim RPC に渡せる信頼されたサーバー専用資格情報であり、クライアントに渡さない。APIロールとバックエンドは設定やリクエスト行を直接変更できない。管理者は対象アカウントの本人確認、利用状況の監査、許可・停止の記録を行う。

新 migration のマージや適用だけでは例外は有効にならない。Dev・ProdそれぞれでReaderによる移行計画を確認し、別途承認された既存Writer手順で適用する。現在のWriter設定・Environment保護を変更しない。PENDING migration の実適用は未検証。アプリの本番ゲートはshared履歴が `IN_SYNC` になるまで停止する。

設定・監査は権限を持つ管理者の承認済み経路で行う。既存Readerは設定の詳細や利用記録を読めず、権限昇格や新たな資格情報の作成はこの機能に含まれない。対象環境の設定操作には別途承認を要する。

- **有効化・再許可:** 対象の認証済み Supabase user ID を確認し、`developer_user_id` に設定する。1人のみ指定でき、対象変更は前の対象を即時無効にする。
- **失効:** `developer_user_id` を `NULL` にする。過去の要求・費用・例外適用時の記録は削除・再分類しない。
- **緊急停止:** 既存の `emergency_stop` は開発者を含む全 AI 新規 claim を停止する。停止・解除は別途承認済みの管理者手順で行う。OCR 例外だけの停止は `developer_user_id` を `NULL` にする。

不明利用を推定値やゼロで精算しない。アカウント削除時は許可を取り消す。
